# Architecture

## Overview

CashFlow Manager is a full-stack web application packaged as a single Docker container for production deployment.

```
┌─────────────────────────────────────────────────────┐
│  Docker container (port 8080)                       │
│                                                     │
│  ┌──────────┐    /api/*   ┌──────────────────────┐  │
│  │  Nginx   │ ──────────► │  Uvicorn / FastAPI   │  │
│  │ (static) │             │  (127.0.0.1:8000)    │  │
│  └──────────┘             └──────────┬───────────┘  │
│       │                              │              │
│  React SPA               SQLite (/app/data/*.db)    │
│  (pre-built)                         │              │
└──────────────────────────────────────┼──────────────┘
                                       │ bind mount
                               ./data/ (host directory)
```

Nginx serves the pre-built React bundle and forwards all `/api/*` requests to Uvicorn on `127.0.0.1:8000`. `supervisord` manages both processes. `start.sh` launches Uvicorn; FastAPI lifespan is the sole automatic migration owner and runs `alembic upgrade head` before the app serves requests.

SQLite startup assumes one app process migrates a given database at a time. Do not overlap direct Alembic commands or parallel app startups against the same database.

## Backend (`backend/app/`)

FastAPI with SQLAlchemy (SQLite) and Alembic for schema migrations.

### Entry points

| File | Role |
|---|---|
| `main.py` | App init, lifespan context (runs migrations + seeds), router registration, CORS |
| `config.py` | `Settings`: Pydantic BaseSettings loaded from environment |
| `database.py` | `Base`, `get_session_factory()` |
| `deps.py` | FastAPI dependencies: `get_db` (DB session), `get_current_user` (JWT cookie → User) |

### Layers

```
routers/     ← HTTP boundary: request parsing, response serialization, auth guard; some small endpoint-specific Pydantic models are colocated here
schemas/     ← Shared and domain Pydantic I/O contracts (decoupled from ORM)
services/    ← Reusable business logic, including database-backed calculations
models/      ← SQLAlchemy ORM models
```

### Models

| Model | Description |
|---|---|
| `User` | Account with optional email, password, and OpenID Connect (OIDC) identities |
| `PaymentMethod` | Bank account or payment instrument (`bank`, card types, prepaid, cash), including main/linked-bank state and optional stamp-duty behavior |
| `Transaction` | Income, purchase, refund, or card-payment record with occurrence date, derived billing month, and optional recurrence linkage |
| `Account` | User-owned saving, investment, or pension account with a stable ID and opening balance |
| `Transfer` | Money movement between stable endpoints; bank endpoints use payment-method IDs and non-bank endpoints use account IDs, with names retained as display snapshots |
| `Asset` | Annual manual override/notes for computed saving, investment, or pension balances, keyed to a stable account when applicable |
| `Category` | User-defined transaction categories |
| `SalaryConfig` | Effective-dated gross salary, contribution/tax rates, benefits, and computed monthly net |
| `TaxConfig` | Effective-dated Italian tax parameters; `user_id=NULL` rows are seeded defaults and user-owned rows are overrides |
| `Forecast` | Saved projection scenario with base year and projection horizon |
| `ForecastLine` | An editable monthly spending-commitment snapshot with amount, reference day, optional source transaction/category/payment method, and notes |
| `ForecastAdjustment` | Per-line effective-date adjustment: `forecast_line_id`, `valid_from`, `new_amount`, and `adjustment_type` (`fixed`\|`percentage`) |
| `MainBankHistory` | Effective-dated main-bank selection and opening-balance reset |
| `UserSetting` | Per-user key/value settings used for onboarding and tracking start; non-bank opening balances belong to `Account` rows |

All PKs are UUID strings generated by `gen_uuid()`. User-owned models carry a `user_id` FK; seeded `TaxConfig` rows are the exception and use `user_id=NULL`.

User-supplied foreign references that point at user-owned rows are validated at write time. For example, transaction `category_id`, payment-method `linked_bank_id`, and forecast-line `category_id` / `payment_method_id` values must belong to the authenticated user.

### Payment method types

| Type | Billing rule |
|---|---|
| `bank` | Bills current month |
| `debit_card` | Bills current month |
| `credit_card` | Bills next month |
| `revolving` | Bills next month |
| `prepaid` | Bills current month |
| `cash` | Bills current month |

Debit cards, credit cards, and revolving cards require an owned bank `linked_bank_id`. Their card-to-bank links are effective-dated by an explicit first-of-month billing period when relinked; each transaction uses the link active for its `billing_month`. Their cash impact is applied only when that historical linked bank is the effective main-bank history entry for the billing month; unlinked cards are rejected for new activity.

### Transaction direction and cash-impact matrix

`transaction_direction` is interpreted by payment-method type. The API rejects every combination not listed below. Summary outcomes are signed net purchases/payments, so a refund is negative; main-bank balance impact follows the indicated sign in the transaction billing month.

| Payment method | Direction / UI term | Main-bank impact | Summary impact |
|---|---|---:|---|
| `bank` | `income` / Income | + amount | income + amount |
| `bank` | `debit` / Purchase | - amount | outcome + amount |
| `debit_card` | `debit` / Purchase | - amount | outcome + amount |
| `debit_card` | `credit` / Refund | + amount | outcome - amount |
| `credit_card`, `revolving` | `debit` / Purchase | - amount | outcome + amount |
| `credit_card`, `revolving` | `credit` / Card payment | - amount | outcome + amount |
| `prepaid`, `cash` | `income` / Income | no impact | income + amount |
| `prepaid`, `cash` | `debit` / Purchase | no impact | outcome + amount |

### Forecast contract

A forecast projects monthly **spending commitments**, not future bank balances or net cash flow. When a forecast is created, it imports recurring debit purchases with an occurrence in December of its selected base year; income, refunds, and card payments are excluded. The December occurrence supplies the starting amount and reference day, even when it is the only occurrence. A series ending before December or starting after the base year is not imported. Selection uses the transaction occurrence date, not its payment method's billing month.

Imported lines are snapshots: changing or deleting source transactions does not rewrite a saved forecast. Users can add, edit, and delete lines and adjustments independently. All lines project monthly throughout the selected future years. Fixed adjustments replace a line's monthly amount; percentage adjustments apply to its original base amount, not to a preceding adjustment. Adjustment start dates are first-of-month dates within the projection period; monthly and yearly totals sum cent-rounded commitments.

### Routers (all under `/api/v1`)

`auth`, `onboarding`, `accounts`, `payment_methods`, `categories`, `salary`, `tax_config`, `transactions`, `transfers`, `summary`, `assets`, `analytics`, `forecasts`, `user_settings`, `users`

`GET /auth/config` is a public capabilities endpoint. The sign-in page uses it to decide whether to show password sign-in, single sign-on (SSO), or both.

### Services

| Service | Key responsibilities |
|---|---|
| `auth` | Password hashing and JWT creation/validation |
| `forecasting` | Import ongoing monthly debit commitments and project spending totals, not future bank balances |
| `bank_balance` | Compute running bank balance from transaction history |
| `billing` | Resolve billing month for credit card transactions |
| `recurrence` | Generate recurrence instances for a date range |
| `salary` | Gross-to-net calculation (IRPEF + INPS) |
| `tax` | Seed and cache Italian tax brackets |
| `summary` | Monthly aggregation: income, expenses, categories |
| `analytics` | Time-series and category breakdown queries |
| `assets` | Asset value snapshot management |
| `seed` | First-run seed data (tax config) |
| `oidc` | OIDC discovery, token validation, provider logout |

### Structure

```
src/
├── api/            ← One module per domain (typed request/response functions)
├── components/
│   ├── analytics/  ← Charts and filter controls
│   ├── auth/       ← Sign-in and registration forms
│   ├── dashboard/   ← Bank balance, asset widgets, outcome cards
│   ├── forecasting/← Forecast management UI
│   ├── layout/     ← AppShell, Sidebar
│   ├── onboarding/ ← 9-step wizard
│   ├── transactions/← Transaction CRUD and list
│   ├── transfers/  ← Transfer CRUD
│   └── ui/         ← Generic primitives (Button, Input, Modal, Select, Badge)
├── contexts/
│   ├── AuthContext.tsx      ← Auth state (React Context + React Query)
│   └── OnboardingContext.tsx← Wizard state
├── hooks/          ← useAuth, useTheme, domain-specific query hooks
├── pages/          ← Page-level components (one per route)
├── types/api.ts    ← Shared TypeScript interfaces matching backend schemas
└── utils/format.ts ← Currency, date formatting helpers
```

### Data flow

1. `api/client.ts`: Axios instance pointed at `/api/v1` with `withCredentials: true`; Vite proxies `/api` → `http://localhost:8000` in development
2. Pages and feature components call the domain API modules through TanStack Query; `api/queryKeys.ts` defines query keys and targeted mutation invalidations. `hooks/` contains only auth, current-user, and theme hooks
3. JWT is stored as an `HttpOnly` cookie. The frontend never reads it directly.
4. The setup flow shares the app-wide TanStack Query client, so onboarding completion updates the same `['onboarding','status']` cache used by route guards
5. The transfers page uses paged `/transfers?limit=&offset=` fetches and incrementally loads older history instead of pulling the full transfer table in a single request

### Auth guard

`router.tsx` wraps all authenticated routes in `AuthGuard`. Unauthenticated requests to `GET /api/v1/auth/me` return 401 and redirect to `/login`. After sign-in, users with `user_settings.onboarding_complete` set to false redirect to `/setup`.

The setup route uses the shared query cache. Completing onboarding updates the route guard immediately.

OIDC users are matched by `oidc_sub` only. Sharing a verified email with an existing password account does not link the accounts automatically.

## Continuous integration and delivery

- **Continuous integration:** `.github/workflows/ci.yml` runs backend tests on Python 3.14, frontend build and tests on Node 24, pull request title validation, and production Compose configuration validation on every pull request and push to `main`. The multi-architecture image build and amd64 smoke test run on `main` only. Playwright end-to-end tests remain manual.
- **Release:** `.github/workflows/release.yml` runs after successful push checks on `main`. semantic-release creates GitHub Releases and a multi-architecture GitHub Container Registry image for amd64 and arm64, with version and `latest` tags. Rerunning the workflow repairs a missing or incomplete release image without rebuilding complete versioned images.
- **Renovate:** `.github/workflows/renovate.yml` runs the self-hosted Renovate action weekly using `.github/renovate.json` and the `RENOVATE_TOKEN` repository secret. Eligible non-major dependency and lockfile updates auto-merge; GitHub Actions updates require manual review.
- **Registry cleanup:** `.github/workflows/cleanup-packages.yml` runs weekly and retains the newest three complete tagged release images, including `latest` on the newest. It removes stale, partial, and orphaned images.

## Key data invariants

- `billing_month` on a transaction is derived by `services/billing.py` and stored as the first day of a month (`YYYY-MM-01`)
- Bank-balance logic assumes `tracking_start_date` and `MainBankHistory.valid_from` are first-of-month ISO dates. The onboarding schema does not currently enforce that invariant, so new write paths must validate or normalize it.
- `credit_card` and `revolving` transactions bill in the following month; `bank`, `debit_card`, `prepaid`, and `cash` bill in the current month
- New transfer writes resolve active accounts by stable ID. Legacy endpoint names are accepted only when they exactly resolve to a current owned active account and never create an account.
- Recurring transaction instances are linked via `parent_transaction_id` FK back to the originating transaction; `PUT` and `DELETE` on `/transactions/{id}` accept a `cascade` query param: `single` (only this instance), `future` (this + future instances), `all` (entire series)
