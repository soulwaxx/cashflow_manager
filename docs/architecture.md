# Architecture

## Overview

CashFlow Manager is a full-stack web application packaged as a single Docker container for production deployment.

```
┌─────────────────────────────────────────────────────┐
│  Docker container (port 8080)                       │
│                                                     │
│  ┌──────────┐    /api/*   ┌──────────────────────┐  │
│  │  Nginx   │ ──────────► │  Uvicorn / FastAPI   │  │
│  │ (static) │             │  (127.0.0.1:8000)    │  │
│  └──────────┘             └──────────┬───────────┘  │
│       │                              │              │
│  React SPA               SQLite (/app/data/*.db)    │
│  (pre-built)                         │              │
└──────────────────────────────────────┼──────────────┘
                                       │ bind mount
                               ./data/ (host directory)
```

Nginx serves the pre-built React bundle and forwards all `/api/*` requests to Uvicorn on `127.0.0.1:8000`. Both processes are managed by `supervisord`. On startup, `start.sh` runs `alembic upgrade head` before launching Uvicorn, ensuring the database schema is always up to date.

## Backend (`backend/app/`)

FastAPI with SQLAlchemy (SQLite) and Alembic for schema migrations.

### Entry points

| File | Role |
|---|---|
| `main.py` | App init, lifespan context (runs migrations + seeds), router registration, CORS |
| `config.py` | `Settings` — Pydantic BaseSettings loaded from environment |
| `database.py` | `Base`, `get_session_factory()` |
| `deps.py` | FastAPI dependencies: `get_db` (DB session), `get_current_user` (JWT cookie → User) |

### Layers

```
routers/     ← HTTP boundary: request parsing, response serialization, auth guard
schemas/     ← Pydantic I/O contracts (decoupled from ORM)
services/    ← Business logic (pure functions, take db session)
models/      ← SQLAlchemy ORM models
```

### Models

| Model | Description |
|---|---|
| `User` | Account; optional `email`, `hashed_password`, and `oidc_sub` identities |
| `PaymentMethod` | Bank account or payment instrument (`bank`, card types, prepaid, cash), including main/linked-bank state and optional stamp-duty behavior |
| `Transaction` | Income, purchase, refund, or card-payment record with occurrence date, derived billing month, and optional recurrence linkage |
| `Transfer` | Money movement between named bank, saving, investment, or pension accounts; bank endpoints can also carry stable payment-method FKs |
| `Asset` | Annual manual override/notes for computed saving, investment, or pension balances |
| `Category` | User-defined transaction categories |
| `SalaryConfig` | Effective-dated gross salary, contribution/tax rates, benefits, and computed monthly net |
| `TaxConfig` | Effective-dated Italian tax parameters; `user_id=NULL` rows are seeded defaults and user-owned rows are overrides |
| `Forecast` | Saved projection scenario with base year and projection horizon |
| `ForecastLine` | A monthly projection line with amount, billing day, optional source transaction/category/payment method, and notes |
| `ForecastAdjustment` | Per-line effective-date adjustment: `forecast_line_id`, `valid_from`, `new_amount`, and `adjustment_type` (`fixed`\|`percentage`) |
| `MainBankHistory` | Effective-dated main-bank selection and opening-balance reset |
| `UserSetting` | Per-user key/value settings used for onboarding, tracking start, and name-keyed opening balances |

All PKs are UUID strings generated by `gen_uuid()`. User-owned models carry a `user_id` FK; seeded `TaxConfig` rows are the exception and use `user_id=NULL`.

User-supplied foreign references that point at user-owned rows are validated at write time. For example, transaction `category_id`, payment-method `linked_bank_id`, and forecast-line `category_id` / `payment_method_id` values must belong to the authenticated user.

### Payment Method Types

| Type | Billing rule |
|---|---|
| `bank` | Bills current month |
| `debit_card` | Bills current month |
| `credit_card` | Bills next month |
| `revolving` | Bills next month |
| `prepaid` | Bills current month |
| `cash` | Bills current month |

### Routers (all under `/api/v1`)

`auth`, `onboarding`, `payment_methods`, `categories`, `salary`, `tax_config`, `transactions`, `transfers`, `summary`, `assets`, `analytics`, `forecasts`, `user_settings`, `users`

`GET /auth/config` is a public capabilities endpoint used by the login page to decide whether to show password sign-in, SSO sign-in, or both.

### Services

| Service | Key responsibilities |
|---|---|
| `auth` | Password hashing and JWT creation/validation |
| `forecasting` | Build monthly forecast-line and aggregate projections |
| `bank_balance` | Compute running bank balance from transaction history |
| `billing` | Resolve billing month for credit card transactions |
| `recurrence` | Generate recurrence instances for a date range |
| `salary` | Gross-to-net calculation (IRPEF + INPS) |
| `tax` | Seed and cache Italian tax brackets |
| `summary` | Monthly aggregation: income, expenses, categories |
| `analytics` | Time-series and category breakdown queries |
| `assets` | Asset value snapshot management |
| `seed` | First-run seed data (tax config) |
| `oidc` | OIDC discovery, token validation, RP-initiated logout |

## Frontend (`frontend/src/`)

React 19 + TypeScript, built with Vite.

### Key libraries

| Library | Version | Use |
|---|---|---|
| TanStack Query | 5.x | Server state, caching, mutations |
| React Hook Form | 7.x | Form state |
| Zod | 4.x | Schema validation |
| React Router | 7.x | Client-side routing |
| Axios | 1.x | HTTP client |
| Recharts | 3.x | Charts |
| date-fns | 4.x | Date manipulation |

### Structure

```
src/
├── api/            ← One module per domain (typed request/response functions)
├── components/
│   ├── analytics/  ← Charts and filter controls
│   ├── auth/       ← Login and register forms
│   ├── dashboard/   ← Bank balance, asset widgets, outcome cards
│   ├── forecasting/← Forecast management UI
│   ├── layout/     ← AppShell, Sidebar
│   ├── onboarding/ ← 9-step wizard
│   ├── transactions/← Transaction CRUD and list
│   ├── transfers/  ← Transfer CRUD
│   └── ui/         ← Generic primitives (Button, Input, Modal, Select, Badge)
├── contexts/
│   ├── AuthContext.tsx      ← Auth state (React Context + React Query)
│   └── OnboardingContext.tsx← Wizard state
├── hooks/          ← useAuth, useTheme, domain-specific query hooks
├── pages/          ← Page-level components (one per route)
├── types/api.ts    ← Shared TypeScript interfaces matching backend schemas
└── utils/format.ts ← Currency, date formatting helpers
```

### Data flow

1. `api/client.ts` — Axios instance pointed at `/api/v1` with `withCredentials: true`; Vite proxies `/api` → `http://localhost:8000` in development
2. Pages and feature components call the domain API modules through TanStack Query; `hooks/` currently contains auth/current-user/theme hooks rather than one hook per domain
3. JWT is stored as an httpOnly cookie — the frontend never reads it directly
4. The setup flow shares the app-wide TanStack Query client, so onboarding completion updates the same `['onboarding','status']` cache used by route guards
5. The transfers page uses paged `/transfers?limit=&offset=` fetches and incrementally loads older history instead of pulling the full transfer table in a single request

### Auth guard

`router.tsx` wraps all authenticated routes in `AuthGuard`. Unauthenticated requests to `GET /api/v1/auth/me` return 401 → redirect to `/login`. After login, if `user_settings.onboarding_complete` is false → redirect to `/setup`. The setup route uses the same shared query cache as the rest of the app, so completing onboarding immediately unlocks the guarded routes without waiting for cache expiry.

OIDC users are matched by `oidc_sub` only; sharing a verified email with an existing password-auth account does not auto-link the accounts.

## Development vs Production

| Aspect | Development | Production |
|---|---|---|
| Frontend | Vite dev server (`:3000`, HMR) | Pre-built static files served by Nginx |
| Backend | Uvicorn `--reload` (`:8000`) | Uvicorn (`:8000`, no reload) |
| Container | Two separate services (`docker-compose.yml`) | Single container (`Dockerfile`) |
| API routing | Vite proxy `/api` → `:8000` | Nginx `location /api/` proxy |
| Base images | Python 3.14-alpine; Node 24-alpine + Nginx 1.31-alpine | Node 24-alpine (build), Python 3.14-alpine (runtime) |

## CI/CD

- **CI** (`.github/workflows/ci.yml`) — runs backend tests on Python 3.14, frontend build/tests on Node 24, PR-title validation, and production Compose configuration validation on every PR and push to `main`. The multi-architecture image build and amd64 smoke test run on `main` only; Playwright E2E remains manual.
- **Release** (`.github/workflows/release.yml`) — triggers after successful push CI on `main`; semantic-release creates GitHub Releases and a multi-arch GHCR image (amd64 + arm64) with version and `latest` tags. If a release image is missing or incomplete, rerunning the workflow repairs it; complete existing versioned images are not rebuilt.
- **Renovate** (`.github/renovate.json`) — the hosted Renovate App runs weekly before 06:00 Saturday. Non-major dependency and lockfile updates may auto-merge; GitHub Actions updates remain manual.
- **GHCR cleanup** (`.github/workflows/cleanup-packages.yml`) — runs weekly and retains the newest three complete tagged release images (including `latest` on the newest), while removing stale, partial, and orphaned images.

## Key data invariants

- `billing_month` on a transaction is derived by `services/billing.py` and stored as the first day of a month (`YYYY-MM-01`)
- Bank-balance logic assumes `tracking_start_date` and `MainBankHistory.valid_from` are first-of-month ISO dates. The onboarding schema does not currently enforce that invariant, so new write paths must validate or normalize it.
- `credit_card` and `revolving` transactions bill in the following month; `bank`, `debit_card`, `prepaid`, and `cash` bill in the current month
- Recurring transaction instances are linked via `parent_transaction_id` FK back to the originating transaction; `PUT` and `DELETE` on `/transactions/{id}` accept a `cascade` query param: `single` (only this instance), `future` (this + future instances), `all` (entire series)
